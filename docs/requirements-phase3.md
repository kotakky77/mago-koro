## 1. 何のためのアプリか(フェーズ3の再定義)

**「楓馬に何をあげたらいい?」に、毎回答えなくて済むようにする。**

- 渡す相手:**自分の親(実家)。1組・家単位で1アカウント**
- 相手の条件:**月に1回以上会える。メールもLINEも使える。ログインは壁にならない**
- 実在する痛み:**贈り物のたびに「何をあげたらいい?」と聞かれ、その都度考えて返している**

> ### ⚠️ 2026-09-12 の方針転換:**写真を主役から降ろす**
>
> 初版は「祖父母に孫の写真を見せる」アプリとして作られている。だが**渡す相手が
> 月1で会えてLINEも使う**なら、写真はLINEで送ったほうが早く、そもそも実物に会える。
> **一番の売りが、この相手には効かない。**
>
> 一方で**LINEでは解決しないもの**が残る。**「何をあげたらいいか分からない」と
> 「重複購入」。** ほしいものリストと購入報告は、まさにそこを解く機能だった。
>
> → **写真は「見に来る理由」の添え物に降格。プレゼント調整アプリとして渡す。**
> これが「作ってあるのに渡せる気がしない」の正体だった。機能不足ではない。

## 2. 決まったこと

| 論点 | 決定 | なぜ |
|---|---|---|
| 最初に渡す相手 | **実家の祖父母、1組だけ** | esca-car と同じく**相手を1人に絞る**。絞ると要らない機能が見える |
| 祖父母アカウント | **家単位で1つ**(父母で共用) | 父母で相談して決めるので、分ける意味がない。必要になったら分ける |
| 義実家(大湊) | **今回は招待しない** | 実家で手ごたえを見てから。合格ラインをぶらさない |
| 主役の機能 | **ほしいものリスト**(写真ではない) | 上記の方針転換 |
| 写真 | **残すが、強化しない** | R2の認可付き配信は作り込み済み。壊さず置いておく |
| ログイン | **今までどおり必要**(メール+パスワード) | 相手は使える。**ここは壁ではない**と本人が判断 |
| 入力する人 | **楓馬くん本人に聞いて、親が代理入力** | 11歳で自分の意思がある。本人アカウントは作らない |
| お知らせメール | **誕生日の2週間前と1週間前の2回** | ネット注文が届く余裕を見て2週間前。直前にもう一度押す |
| 本番稼働の締切 | **2026-09-25** | 2週間前メールがその日に出る。**10/9ではない** |
| 合格ライン | **10/9に、実家が「リストから選んで」贈ってくれる** | 網羅でも作り込みでもなく、**一度使われるか** |

## 3. コードを読んで分かった穴

現行実装は **「贈る側が1組だけ」の前提**になっている。

1. **買う前に「これにする」と表明する手段がない。**
   `wishlist_items.purchased` が立つのは購入報告を押した瞬間だけ。つまり**買った後**。
2. **祖父母の画面に「誰が」が出ていない。**
   `purchased_by_id` は保持しているのに、`views/grandparent.tsx` は「購入済み」タグのみ。
3. **ほしいものリストのURLが必須**(`routes/wishlist-items.tsx` の `parseWishlistForm`)。
   本人に聞いて入れる運用だと「サッカーボール」のようにURLの無いものが入れられない。

→ 1 は実家と自分たち夫婦の間でも起きる(**親 vs 祖父母の重複は実在する**)。
→ 2 は義実家を入れた瞬間に効く。3 は **9/25 までのリスト入力で自分が詰まる。**

## 5. 実装の決定事項(2026-09-12 に確定)

**着手前の論点はすべて潰した。以下のとおり実装する。**

### 5.1 「事前表明」の持ち方 → **案A:列を足す**

`wishlist_items` に **`reserved_by_id` / `reserved_at` を追加する。**

- **既存の購入フローには一切触らない。** `purchased` / `purchased_by_id` / `purchased_at` はそのまま
- 却下した案B(`status TEXT` に作り替え):3状態で整理はされるが、`lib/db.ts` と
  `views/*.tsx` の既存箇所を広く書き換えることになる。**実質13日しかないので安全側を採る**
- `purchased = 1` になったら、表示は**購入済みを優先**する(`reserved_*` は履歴として残す)

**取り消しは許す。おさえた本人と、親の両方が解除できる。**

- 高齢者向けアプリなので**押し間違いは前提**。解除できないとその品が**永久にロックされる**
- 親も解除できるようにするのは、祖父母が操作に詰まったときの逃げ道として
- ⚠️ **記念品の注文ステータスは「一方向遷移のみ」という設計判断をしているが、ここは揃えない。**
  注文は実際に商品が動くが、**事前表明は気持ちの表明**にすぎないため。理由が違えば設計も違ってよい
- **自動失効は作らない。** 誕生日という短い期間なので実害が小さい。親が解除できれば足りる

### 5.2 Cron(誕生日お知らせメール)

| 項目 | 決定 | 理由 |
|---|---|---|
| 発火時刻 | **`"0 23 * * *"`(JST 8:00)** | birthday-reminder が `"0 22"`(JST 7:00)。**ずらして2通同時着弾を避ける** |
| 対象の引き方 | **「14日後/7日後の日付」を先に計算し、その月日と一致する `children` を引く** | 逆向き(誕生日に日数を足す)にすると**年跨ぎ(12/30 + 14日 = 1/13)で壊れる** |
| 二重送信防止 | **送信ログテーブル + UNIQUE制約** | Cronの再試行で2通届くのが一番かっこ悪い |
| 宛先 | `invitations` の `status = 'accepted'` → `grandparent_id` → `users.email` | |

送信ログ:`(child_id, grandparent_id, kind, sent_on)` に **UNIQUE**。`kind` は `'d14'` / `'d7'`。

- `wrangler.jsonc` に `triggers.crons` が**まだ無い**。`src/index.ts` に `scheduled` ハンドラも無い。両方追加する
- `lib/gmail.ts` の `getGmailAccessToken` / `buildMimeMessage` / `sendGmail` がそのまま使える。
  本番の secret は登録済み(パスワードリセットで稼働中)

### 5.3 URL必須 → **任意にする(マイグレーション不要)**

**楓馬くんが実際に挙げた2つが、どちらもURLを持たない**(§5.5)。ここで即詰まる。

- **`url TEXT NOT NULL` のまま、空文字を許す。** これで**マイグレーションが要らない**
- `routes/wishlist-items.tsx` の `parseWishlistForm` から**URL必須チェックを外す**
  (入力があったときの `^https?://` チェックは残す)
- 表示側(`views/wishlist.tsx` / `views/grandparent.tsx`)の「商品ページを見る ↗」を**条件表示**に
- **既存データは全件URLありなので影響ゼロ**

### 5.4 メール文面

- **1通1用件。**「楓馬くんが10月9日で11歳になります」＋ **ほしいものリストへの直リンク**、以上
- 高齢者向けガイドライン(16px以上・高コントラスト)は画面の話だが、**文面も同じ配慮で**書く
- 送信元は `GMAIL_FROM`(`geiruzusi@gmail.com`)

### 5.5 初回リストの中身(2026-09-12・本人に確認済み)

**楓馬くん本人が挙げたのは2つ。**

| # | ほしいもの | 扱い |
|---|---|---|
| 1 | **スマホ、またはタブレット**(本人の理由:「好きな時にYouTubeを見たい」) | **載せる。ただし説明欄に「親と相談のうえ」と明記する** |
| 2 | **一緒にウォーキングするための靴**(イッセイくんと歩くため) | **そのまま載せる** |

- 1は**高額かつ、持たせるかどうかが親の判断**を含む。買う前に必ず連絡が来るよう、説明欄で条件を示す
- **2件とも購入先URLを持たない** → §5.3 の判断につながった
- 価格帯が大きく開く(数万円 / 数千円)。祖父母が選びやすいよう、**分かる範囲で `price` を入れる**
- ⚠️ 2は健康・家族のテーマとつながっている(`my-assistant/健康/方針.md` の
  「歩く予定を月1で入れる」/ `my-assistant/家族/STATUS.md` の「親としてやると決めたこと」)
